Syrvis
User guideDesignProvabilityGitHub

Site reliability and systems engineering practice, brought to your Synology NAS on top of DSM

Syrvis runs beside DSM and manages the services on your server. You declare what the server should run, and syrvis starts, stops and brings those services back in the right order, through deployments, reboots and power cuts, and shows you where the server differs from what you declared.

Overview

What syrvis adds to your server

Teams that run large online services keep them up with a handful of shared habits. Syrvis brings six of them to one Synology NAS. DSM still runs the server and Container Manager still runs the containers; syrvis decides what runs, in what order, and checks the result. You drive it from your own computer with one command, syrvis.

Declared state

One document says what the server should run. Syrvis brings the server to it and reports where the two differ.

Ordered stops and starts

Services stop with what depends on them first and start in the mirror order, for a deployment, a drain, a reboot, a power-off or a power cut.

Plans before changes

Every change is staged and planned first. The plan shows what will stop and start, in which waves, and how long it may take.

Durable workflows

A long procedure writes each step down as it goes, so it picks up after a crash or after the reboot it asked for.

Health against what you declared

Health compares what the server runs with what you declared. A service you stopped on purpose reads as drained, and only a difference you did not ask for needs you.

One API

The syrvis command, the console, an AI agent and the OpenTofu provider reach the same named calls. A grade, a refusal or a confirm behaves the same from each.

Built for one server, on purpose

Orchestrators built for clusters spend much of their design on keeping many machines in agreement. Syrvis runs on one server, so one process holds the truth, and it keeps the habits worth having without that machinery. It depends on Go's standard library and its own modules, and nothing else.

Order and power

One graph of what needs what

Each service lists the services it depends on, such as an app that needs its database to be healthy before it starts. Services also form groups, and a group names what it provides and what it requires by the need, such as metrics, instead of by a product. Each requirement binds to exactly one group that provides it, or syrvis refuses the deployment and names the candidates. Swap your monitoring for another and only the binding changes; no service that uses it is edited.

A power cut at night

The times and services below are an example. Syrvis acts on the battery's reported time, and nobody has to be awake.

  1. 2:07

    The power fails and the UPS takes over

    Your UPS reports how long its battery can last, 14 minutes in this example. Syrvis has already computed how long an ordered stop of your services takes, from what each service declared.

  2. 2:08

    Syrvis waits while the battery allows

    It counts the UPS's reported time at 70 percent and waits while the battery affords it. If the power comes back and holds, the workflow ups-restore brings back whatever was stopped.

  3. 2:12

    Services stop in order

    What depends on a service stops before it, at most two at a time. The database stops after the services that use it. The monitoring stops last, so the whole stop is recorded.

    media-web→media-api→media-db→metrics-db, last
  4. 2:14

    The server powers off

    With every service stopped, the workflow hands the power-off to DSM. DSM's own low-battery shutdown stays as the last resort if the daemon is not running.

  5. 6:40

    The power is back and the server starts

    Syrvis releases the drain and starts the services in the mirror order: monitoring first, then the database, then what uses it. Each service is started and held until it is ready before the next one starts.

    metrics-db, first→media-db→media-api→media-web
  6. 7:15

    You check the server

    ● healthy   nothing needs you

The stop and the start, service by service

Five uses of one graph

  • Deploying. A deployment is checked against the graph when you stage it, and refused with the fix named if a need is unmet or met twice. The apply's waves follow each service's own dependencies; group edges are not yet part of the apply.
  • Draining. One command stops a set of services in order, with a time budget computed from what each service declared.
  • The stop on battery. The same drain, started by the daemon when the UPS reports a power cut. Adding a service lengthens the budget by itself.
  • The planned reboot and power-off. syrvis reboot and syrvis power-off drain the server, wait until it is ready, and restore the services after the boot. You press restart in DSM yourself.
  • The start after boot. The mirror order, one service at a time within a wave, for a start syrvis orders; after a crash, Docker's own restart policy may start containers first. Starting a group only when what it provides is healthy is designed, not built.

Managing and visibility

Managing the server, and seeing what it does

Everything syrvis does is a named call on one API, served by the daemon, the program syrvis runs on the server. Four things reach that API.

Terminal

The syrvis command

One program on your computer for every act: install, status, deployments, drains, reboot, power-off, workflows and seats.

Browser

The console

syrvis dash opens a read-only view of the server in your browser: services, deployments, workflows, chores, checks, events and access. It changes nothing.

AI agents

The agent bridge

syrvis mcp lets an AI agent that speaks MCP reach the same calls, with the seat of the connection it runs under. It cannot stage a deployment, and it can deliver a confirm you made but never make one. No AI agent has been tested with it yet.

Infrastructure as code

The OpenTofu provider

Keep the whole deployment in a file and change it with tofu plan and tofu apply. Optional, and not released yet; the Your services tab says where it stands.

Seats and grades

Each computer that connects holds a seat: its own key, a grade and an expiry, recorded on the server. A read-only seat reads. An operator seat also makes changes: stage, plan, apply, drain, reboot and power-off. An admin seat is granted only at the server and can add other seats. Rollback, prune and granting admin work only at the server itself. Prune, rollback, move and power down ask you to type a challenge, and no flag skips it. No password exists, and syrvis never opens a shell on the server.

Seeing what the server is doing

Run syrvis status. When the server matches what you declared:

Workflows

Long procedures that survive a restart

A workflow is a procedure the daemon runs step by step, writing each step to its journal before it moves on. So it carries on after a daemon restart or after the reboot it asked for, and a step that may have run when the server crashed is held for you instead of being run twice.

Your services

Running your own services

One document declares any container you want to run, and syrvis plans it, orders it among your other services and watches it. Today you write that document by hand. A catalog of vetted services and a first service in one command are decided and not released.

What you need

  • A paired server with Container Manager.
  • An operator seat.
  • For a service that keeps data, a placement file you write by hand and put in place with a root line at the server.

Stage, plan, apply

Staging stores your document as a new revision and checks it against the graph. Nothing on the server changes yet.

syrvis --context nas stage < bundle.json

The plan says what will stop and start, in which waves, and the time budget. <revision> is the id that stage printed.

syrvis --context nas plan <revision>

Then apply it, and watch the job it starts:

syrvis --context nas apply <revision>
plan revision rev-7 (budget 1m30s = stop 20s + bring-up 1m10s, max_parallel 2)
  name    action    phase  charge
? web     recreate  both   60s
? worker  recreate  both   30s
  1 service(s) already converged (none)
  stop waves:     [web worker]
  bring-up waves: [worker(running)] → [web(healthy)]
  pulls (pre-flip, outside every budget): web:1.5

✓ job job-deploy-12 started (budget 1m30s), watch with: syrvis job job-deploy-12 --watch

A minimal document has this shape. It is the shape the tests use, and it has not been run on a server as written.

{"schema": "syrvis-bundle/3",
 "declarations": {"schema": "syrvis-declarations/4",
   "networks": [{"name": "example-net"}],
   "services": [{"name": "web", "spec": {"image": "registry.example/web:1", "network": "example-net"}}]}}

Images are pinned by tag or by digest. syrvis revisions lists earlier revisions; the server keeps the newest ten, the current one and the rollback target. A rollback runs only at the server itself.

The OpenTofu provider

If you keep your configuration as code, the OpenTofu provider holds the server's whole deployment as one resource. tofu plan stages and plans, tofu apply applies only the plan you reviewed, and tofu destroy forgets the state and changes nothing on the server. Secrets come from sops and are rendered in memory on your computer.

provider "syrvis" { address = "tls:nas" }
resource "syrvis_deployment" "box" {
  device   = "nas"
  services = { example-svc = { enabled = true, spec = { image = "<registry-host>/<repository>@sha256:<64 hex>" } } }
}

The provider is built and tested against a real daemon and real OpenTofu; a test layer against a real server is not built. It is not released yet: there is no release tag, and you place the plugin by hand. It grants no seats: a plan that names a seat fails and prints the command to run at the server.

Decided, not released

  • A catalog of vetted services, and syrvis catalog.
  • A first service with no OpenTofu.
  • An install that writes the placement file for you.

Install

Pairing your computer with the server

The install runs from your computer, with one command and five steps of yours. No password is created. Only the public half of your computer's key travels, and you carry it to the server yourself, through DSM, where you are already signed in as an administrator.

Your five steps

  1. Run syrvis install. It downloads the server's package and the installer, checks both against the release's checksums, and makes your computer's key.
  2. In DSM, install the installer with Package Center's Manual Install. Your computer's key is already in its one field.
  3. Choose which shared folder is syrvis's home.
  4. In Task Scheduler, create a task named "syrvis root" that runs as root.
  5. Paste the root line into that task and press Run.

DSM lets no package install another or run as root, and a root task can, so the last step is yours. The root line carries a 16-character code, a digest of your answers, and the root step applies only answers with that digest. Then the daemon starts, your computer's key becomes its first seat, and your computer pins the daemon's key: it records that key and accepts no other.

✓ root step   ran on the box                                     1m4s  5/5
✓ paired      nas at 127.0.0.1:50002, its key is the one the installer sent

Installed SyrvisCore 2.0.0 on nas in 14m56s. All 5 of your steps done.

From then on every call is mutual TLS: your computer checks the daemon's key, and the daemon checks your computer's seat. If you close the window partway, run syrvis install again; each side keeps a journal and picks up at the step it reached.

Your computer's first connection to the installer is taken on trust on your local network, and the screen says key unchecked. A one-time code that proves the server to your computer at that first meeting is decided and not built.

What you need

A Synology NAS with DSM and Container Manager; the install checks for Container Manager and stops with the way on if it is missing. Server release 2.0.0-alpha.72 and syrvis v0.1.13. Syrvis is alpha and its code repositories are private for now, so today both come from release pages that need read access to the syrvis organisation.

Building blocks

How syrvis is put together from Go building blocks

Syrvis is more than one program. The daemon on your server, the installer that sets it up and syrvis on your computer are each assembled from the same five Go libraries: a workflow engine, a deployment service, a transport, a set of shared layers called the commons, and a client library. Another daemon or tool can be assembled from them the same way.

Two rules make this work. First, each library uses Go's standard library and, beyond it, only syrvis's own modules (a module is a versioned unit of Go code), each pinned to a version and copied into the repository, so a build never reaches the network; the OpenTofu provider is a named exception and also uses HashiCorp's plugin framework. Second, one implementation stands behind every way in: each library ships its own contract package, the method names and wire types it offers, and the daemon seals them into one list of methods. One dispatcher, one check of what each seat may do and one wire client stand behind syrvis, the agent bridge and the provider, so a capability added for one reaches all three.

The engine

The engine runs workflows: lists of steps that must finish even if the server restarts halfway through. It lives inside the program that uses it and remembers every step across restarts. Each workflow is a definition compiled into that program.

  • It is one Go package that uses only the standard library, with no socket and no separate program to run. Two engines in one program share nothing.
  • Every fact goes into one journal, an append-only record written through to disk before an act counts. A step whose outcome the engine cannot know is reported as unknown and held for a person to decide.
  • Its design is a TLA+ model, a description of the system's states that a checker tries one by one. Twenty-seven duals, copies of the model with one guard switched off that must fail, prove the checker catches each break, and code lands only after its model passes.

Engine

The deployment service

The deployment service keeps track of what your server should run. It stages a new revision, plans it, applies it, rolls it back and prunes old ones, and brings the server to match. When the server drains, stopping its services in order, the deployment service drains with it.

  • While a drain stands, it refuses any deployment that does not come from syrvis itself.
  • Its TLA+ model has twenty-two duals, covering the order services stop in, the order they come back in, never two containers, and a tombstone (the record that something is gone) written before anything is erased.
  • Its methods and wire types are its own contract package, deployapi.

Deployment

The transport

The transport is the encrypted link between the daemon and every program that talks to it. It uses mutual TLS, so both ends prove their key when the link opens. It also holds pairing, which introduces your computer to your server, and seats, each computer's permitted key on the server.

  • Once paired, a program trusts exactly one key, named by its pin: the SHA-256 hash of that key. No certificate authority vouches for the key, and no hostname is checked.
  • It uses only the standard library and holds no state. Both ends run one shared test from fixed test vectors, so the side that dials and the side that listens agree.
  • One package, dial, is the only one allowed to open a socket to the API.

The commons

The commons holds the layers every daemon builds on, below any one service. It is one repository of seven Go modules in a strict order: primitives (facts, the journal, events), declarations (what the server is told to run), adapters (DSM actions and a Docker client), probes (how the server is read), grading (status and health), frame (method dispatch, confirms and the lifecycle) and secretstore (one sealed document of secrets, each found by its key id).

  • Every observed value carries three things: whether it was answered, when it was observed, and why it could not be reached. A value nobody answered never counts as healthy.
  • Each module imports only the modules below it. A test, TestModulesFormNoCycle, and one wall per module hold that order; a wall is a test that refuses an import across a boundary. One release tags all seven modules at one version.
  • A program takes only the layers it needs: the deployment service takes five, the provider two. The census grader works with no state store and no Docker, so it can still read the server during a rescue.

Commons

The client library

The client library is what a program needs to talk to the daemon, packed so that any program can embed it. syrvis on your computer is built on it, and the console's unreleased code uses it too. A program with no terminal at all can use it the same way.

  • It runs its own copy of the engine, one for each server connection you have saved, kept in a folder under your settings, or in memory for read-only use.
  • A wall over every package it exports forbids exiting the program, printing, reading the keyboard, parsing flags, listening for connections and running other programs, so any program can embed it.

Client

One engine, two places

The engine the daemon runs on your server also runs inside syrvis on your computer. The client library opens one engine for each server connection, with its workflow definitions compiled in. The daemon starts its engine when it boots; syrvis starts one each time you run it, and that engine replays what it remembers, takes its next steps and exits. The same transport dials from syrvis and listens in the daemon. The installer is a second program in the daemon's repository, built from the same blocks.

More is designed and not built: a smaller daemon, which today is a profile of the daemon; a lighter instance with the engine, chores, a pager and the dial, and no door (the listening side that accepts connections); an outside home automation daemon made of the engine, a bus and the dial; and a program of the console's own.

Syrvis is alpha, and its code repositories are private for now; only the repository that holds this site is public. A repository link on this tab opens only for a person with read access to the syrvis organisation on GitHub.

Advanced

The algorithms and the trades behind them

This tab is for engineers who want the design under the surface: each algorithm or decision, why it was chosen, and what it costs. Each item links to the design page that holds the detail.

One writer and the state fence

One daemon process holds the truth. It takes a single lock on its state folder, and each library owns one folder under that fence and no other file. With one writer there is nothing to agree on, so syrvis carries no consensus, quorum or leader election. The cost is availability: syrvis is not highly available, and more than one daemon is planned, with none of it built.

Design, How the daemon composes themDesign, More than one daemon

Plain files, a journal and one rename

State is a JSON snapshot and a checksummed journal behind a narrow store interface. A change lands by writing a staging directory or a temporary file, fsyncing it, and moving it into place with one atomic rename; current is a regular file because a symlink cannot be fsynced. So a revision directory that exists is whole, and an interrupted apply needs no undo log. An embedded SQLite was the earlier escape hatch and is retired, which gives up a query language over the state.

Deployment, The storeEngine, The journal

A durable work queue with leases

The queue is derived from the journal at replay; no broker holds it. A work item is one attempt of one step, keyed by (instance, step) on every attempt, offered until a runner begins it, and Begin journals begun once per attempt, so the offer is at least once and the effect at most once. Exactly-once is not claimed: an item begun when its lease is lost holds as outcome_unknown for a person and is never begun again. Emergency items are offered first, and a reserved worker means the stop on battery never waits behind ordinary work.

Engine, The queue and its leasesEngine, What it leaves out

Timers journaled at entry, and the boot id as the epoch

The engine assumes one host, one clock and one writer, so it carries no partition or clock-skew machinery. A timer's instant is journaled when the wait begins, so it fires once across restarts, and a wait on the boot is answered from the boot id, the epoch that tells one boot from the next. A lease token names the engine's epoch, so a stale token begins nothing. None of this stretches to a second host as it stands.

Engine, Waits and human confirms

The lifecycle table and its admission

Whether a reboot, a shutdown, a drain or an apply may start is answered by one table held in memory, in place of distributed locks and fencing tokens. One reboot or shutdown stands at a time. Apply, rollback and prune ask the table first, so each refuses while the server drains and names the state and the way on. The table belongs to one daemon on one server and answers for nothing beyond it.

Commons, The lifecycle table and its admissionDaemon, Power and the lifecycle

The capability resolver

Each requires binds to exactly one provider, in this order of precedence: the group's own bind, then a default in the server's config, then the only group that provides it; anything else is refused. The five refusals are capability_unprovided, capability_ambiguous (naming every candidate), bind_unknown_group, bind_not_a_provider and capability_cycle (naming the cycle in order), and a document that does not resolve never becomes a revision. Each binding becomes edges in the one service graph: every member of the requiring group stops strictly before every member of the provider and starts strictly after it, strictly because members of one wave stop concurrently. A deployment with no groups plans byte for byte as before; the apply's own waves do not yet use group edges, and readiness by capability is designed, not built.

Deployment, Stop and start orderDeployment, Revisions and the plan

The drain budget, computed from the plan

The time a drain needs is computed from the plan the executor will run: each member's declared stop_max_sec, the waves, the parallelism (at most two stops at once by default), the floor last, and the group edges. Each member climbs a ladder on its own window: ask to stop, poll, one kill, verify, report. On battery the daemon reads the UPS's reported runtime at 70 percent, waits while the battery affords it, then runs the drain and the power-off with no confirm. A broken group declaration refuses a deployment but never the battery drain, which falls back to service-level order and says so; the battery path is built.

Deployment, Stop and start orderScenarios, When the power goes out

Mutual TLS with pinned keys and seats, and no certificate authority

Your computer mints an Ed25519 key and only the public half travels; each side pins the other's key by the SHA-256 of the public key, with no certificate authority and no hostname check. Each computer holds a seat, a roster row with a grade and an expiry, renewed 21 days before it expires; a seat's life ends 730 days after it was granted, and a key rotation started on your computer brings it back. The destructive class answers only at the local socket on the server, which reads its caller from the socket's peer credentials. The cost is that trust begins at first meeting: the installer's key is taken as first met, and the one-time code that would prove it is decided and not built.

Transport, The pinTransport, Seats and their life

The install as two journaled workflows on two machines

The install is where distribution remains, so syrvis uses the pattern in full: your computer and the installer each run their own journaled workflow (the installer's steps are open, paired, received, answered, rooted, served, down). Each call between them is retried under one key against a handler that is idempotent by that key, and the receiver journals before it answers, so closing the laptop mid-install loses nothing. Root learns what to apply from the first 16 hex characters of the SHA-256 of the answers document, and refuses a document with another digest or another computer's key. The installer pairs once and stops, so pairing again needs an uninstall and a fresh Manual Install.

Health as conformance

Health is the conformance of what the server observes to what was declared, never uptime. A fact the server cannot answer grades unknown, and unknown is never a pass; a drained service reads as drained. The same groups roll up a verdict and a drain budget per group. The cost is the declaration itself: what nobody declared is not graded.

Daemon, Health as conformance to declared intent

Zero dependencies, and the one exception

Every module of the product requires the Go standard library and, beyond it, only first-party syrvis modules pinned to a tag and vendored, so no build gate reaches the network. The reason, in the record's words: zero third-party runtime dependencies "is itself a static guarantee: less surface to analyze, nothing unaudited in the binary"; an embedded message broker was rejected on this ground, and nothing else is installed on the server, no database, broker or language runtime. The one exception is the OpenTofu provider, which keeps the Terraform plugin framework, runs only on your computer and is optional; a build guard holds the daemon's own module to the standard library. The cost is that the journal, the store, the queue and the transport are syrvis's own code to keep.

How TLA+ is used

The libraries that hold state carry TLA+ models: the daemon, the workflow engine, the deployment service and the commons. TLC, the TLA+ model checker, runs every model in each repository's make check gate, and a missing checker fails the gate. Each guard has a broken twin, the model with that guard turned off, which must fail on its named property, so no proof passes by vacuity. In the engine, trace tests replay behaviours that TLC generates against the Go code.

Five of the properties checked for the stop and start order:

  • FloorStopsLast: no floor member is asked to stop before every other member has stopped.
  • RestoreMirrorsStop: a device restore starts the floor first, then dependencies before dependants.
  • CycleRefuses: a drain over a dependency cycle stops nothing and refuses.
  • StopEnds: every stop plan ends within its budget, even if a container never dies.
  • NoApplyUnderDeviceDrain: no apply, rollback or prune is admitted under the device drain.

A green run covers the model's bounds and nothing past them, and it says nothing about the Go unless a test ties the code to the model. The provability pages say, model by model, what each proves and what it misses.
